Trade requests batch API reference

Status: This topic documents the batch POST method, which is fully available. The single-request methods (GET, PATCH, and DELETE) are work in progress and will be available soon.

The Trade requests API manages trade request data, including creation, updates, and termination. Each request contains a set of pre-configured items that are delivered to, and paid for by, the account associated with the request.

Base URL /v1/trade-requests
Authentication All APIs require a client ID and a client secret. For details, see the global authentication documentation.
System parameters System parameters for this API are in the Northstar knowledge base, under System parameters > Logistics > Trade (TR).

Supported methods

Method Endpoint Description Limits and notes
POST /v1/batch/trade-requests Creates many trade requests in bulk. Accepts a JSON file containing an array of trade requests in the format of the POST /v1/trade-requests request body. Returns 201 Created immediately with a URL to track the batch job. The hard limits depend on the optional skipApproval parameter: 12 request lines and 37,000 database rows (skipApproval=false) or 1,000 request lines and 1,550,000 database rows (skipApproval=true).

Method details: POST batch

The batch endpoint is designed for high-volume imports. It accepts a multipart upload with a JSON file, processes the data asynchronously, and returns a job identifier so you can monitor progress and review any failed requests.

Request structure

Submit the request as a multipart form upload:

  • Header: content-type: multipart/form-data
  • Body: One form-data field. Leave the name empty and attach the JSON file as the value.

Operational behavior

The batch API does not accept a JSON object in the request body. It expects a JSON file. GZIP-compressed files are also accepted when the upload exceeds the framework's size limits. Use the basic example for the minimum valid payload and the complete example for the full field set.

The request is asynchronous. The endpoint returns 201 Created immediately, and the location response header contains a URL to track the batch job. Use the Batch jobs API to monitor the process:

  • GET /v1/batch-jobs/{batchJobId}/status: Checks whether the job is queued, running, completed, or failed.
  • GET /v1/batch-jobs/{batchJobId}/results: Downloads the results file for failed requests. Add the optional view=created parameter to receive a summary of successfully created requests.
  • POST /v1/batch-jobs/{batchJobId}/cancel: Cancels a running job.

Valid requests are saved per page. The system stores 100 trade requests at a time as it processes the file.

Invalid requests are not saved. Error details are available through the results endpoint. To retry, correct the failing entries and resubmit them in a new batch request.

Multi-entity capability. All trade requests in a batch are created in the same business entity. The optional entityId query parameter determines the target entity, for example POST /v1/batch/trade-requests?entityId=123. If the parameter is omitted, the system uses the authenticated user's default entity. If provided, the user must have permission to that entity. Any entityId value in individual request objects is ignored.

Limits

The batch endpoint uses two hard limits:

  • The maximum number of request lines per trade request.
  • The maximum total number of database rows generated by the call. Database rows represent the sum of the request header, line, and ledger rows created by the batch. Use the following formula: Database rows = SUM(1 + number of request lines × 3). For example, a batch of two requests with 4 and 5 lines creates (1 + 4 × 3) + (1 + 5 × 3) = 13 + 16 = 29 database rows.
Note: The formula is an estimate based on average request complexity. The actual row count depends on the configuration of each request.

The limit values depend on the value of the skipApproval flag.

Limit skipApproval=false (default) skipApproval=true
Maximum request lines per request 12 1,000
Maximum database items per call 37,000 1,550,000
Maximum requests per call (all requests at the maximum number of lines) 1,000 requests with 12 lines 516 requests with 1,000 lines. If all requests have 10 lines, up to 50,000 requests.
Approval tasks Generated for each line of the successfully created requests. Not generated. You can still print, pick, and invoice the requests normally.

General rules:

  • The file must be a valid JSON array. Each element follows the request body structure of POST /v1/trade-requests.
  • Automatic request number assignment is allowed if the request uses a number type with an automatic assignment method.
  • Make sure that enough posting periods are available for the volume of requests.

Validation rules

Note: Because the request is asynchronous, hard-limit and validation errors are not returned directly. Review them through the batch jobs results endpoint.
POST_001: User is not authorised (401)

Given a batch of new trade requests to create, when you call the POST batch method, but the user does not have permissions, then the API is not reached and a 401 Unauthorized response is returned.

Example error message: "Unauthorized."

POST_002: File not sent with the request (400)

Given a batch of new trade requests to create, when you call the POST batch method, but you have not attached the JSON file, then the API is not reached and a 400 Bad Request response is returned.

Example error message: "File not present in multipart content."

POST_003: Hard limit exceeded for request lines (201)

Given a batch of new trade requests to create, when you call the POST batch method, but one or more requests contain more lines than the hard limit, then 201 Created is returned immediately. When the job finishes, the status endpoint returns a jobResult of CompletedWithErrors, and the results endpoint returns the failing requests with an error message for each request.

  • Without skipApproval: "The number of lines per request exceeds the maximum allowed limit of 12."
  • With skipApproval: "The number of lines per request exceeds the maximum allowed limit of 1000."
POST_004: Hard limit exceeded for database items per call (201)

Given a batch of new trade requests to create, when you call the POST batch method, but the number of database items to store exceeds the hard limit, then 201 Created is returned immediately. When the job finishes, the status endpoint returns a jobResult of CompletedWithErrors, and the results endpoint returns the failing requests with an error message for each request.

  • Without skipApproval: "The number of items to be saved will exceed the maximum allowed limit of 37000."
  • With skipApproval: "The number of items to be saved will exceed the maximum allowed limit of 1550000."
POST_005: All requests are valid (201)

Given a batch of new trade requests to create, when you call the POST batch method, then 201 Created is returned immediately with a URL to track the batch job. When the job finishes, the status endpoint returns a jobResult of Completed. By default, the results endpoint returns an empty array. With the optional view=created parameter, it returns an array of summarised objects for the stored requests.

POST_006: Partial success, some requests are invalid (201)

Given a batch of new trade requests to create, when you call the POST batch method, but one or more requests contain validation errors, such as an invalid account, a missing required field, or an invalid item, then 201 Created is returned immediately. When the job finishes, the status endpoint returns a jobResult of CompletedWithErrors, an errorCount with the number of failed requests, and processedCount with the total number of processed requests. The results endpoint returns only the failing requests with their errors. With view=created, it returns only the created requests as summarised objects.

POST_007: Duplicate request number (201)

Given a batch of new trade requests to create, when you call the POST batch method, but one or more requests use a request type that requires manual request number assignment and the request number already exists, then 201 Created is returned immediately. When the job finishes, the status endpoint returns a jobResult of CompletedWithErrors, and the results endpoint returns the failing requests with an error message for each request.

Example error message: "Request number already in use."

POST_008: User does not have access to the specified entity (403)

Given a batch of new trade requests to create, when you call the POST batch method with an entityId query parameter, but the authenticated user does not have access to that entity, then the request is rejected before the batch job is processed and a 403 Forbidden response is returned immediately.

Example error message: "User is not authorised."

Best practices

  • Use the single-request endpoint for individual requests. To create one trade request, use the synchronous POST /v1/trade-requests endpoint. Use the batch endpoint when you need to create many trade requests at once.
  • Check the results to handle partial failures. When the status endpoint reports failures, call the results endpoint to get the requests that were not saved. Fix the errors and resubmit those requests in a new batch call.
  • Use the same requestType for all requests in a batch. A known issue can cause unexpected request number assignment when a batch mixes requests with different request types. Group requests by type and submit them in separate batch calls where possible.

Related APIs

  • Items API: Manages the item master entries that request lines use.
  • Accounts API: Manages the account information you use when you create trade requests.
  • Query API: Queries trade request documents (read-only).
  • Batch jobs API: Tracks the status and results of batch jobs.

For interactive request and response schemas, see the Swagger UI for the Orbis API.
