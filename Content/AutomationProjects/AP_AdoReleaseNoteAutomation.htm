AI automation project: from work items to reviewed release notes

The goal of the project is to remove the manual steps between a fixed customer issue and a release-note entry that is ready for review, so that a technical writer only needs to check and approve the text.

This project is an artificial intelligence (AI) agent that turns Azure DevOps work items into release-note entries in a MadCap Flare project. It reduces manual triage and keeps every rule, decision and change visible and traceable.

Problem

Release-note work starts in Azure DevOps. A fixed issue sits among user stories, tasks, related items and ported copies of the same fix. Only some of these records are customer-facing, and fewer still need a release-note entry.

Before the writer can draft an entry, the writer must complete several checks. The writer must find the right record, confirm that it qualifies and look for an existing documentation task. The writer must then identify the release, locate the topic and confirm that the fix is not already documented.

The starting point also varies. A request can name a single work item, a list of items, a saved query or a parent item that holds the real issue at a deeper level of the hierarchy. The workflow must decide when to expand the hierarchy, when to stop and which rules take precedence.

Purpose and approach

Writing the entry is the smallest part of the job. Most of the effort goes into the surrounding checks and the record keeping that lets the team trace each change.

The agent performs those steps end to end under written rules, and it stops to ask when a rule cannot be applied. The AI model drafts the text, but it does not decide the process. Version-controlled Markdown files define the process, so the behaviour is predictable, reviewable and easy to change.

The rules live in files, the agent follows them, and every run ends with a summary that a person can check.

Tools and technologies

The workflow uses the following tools and file types.

  • GitHub Copilot in Visual Studio Code supplies the chat interface, the language model and the agent runtime. In agent mode, the model can call tools and read and edit files in the workspace.

  • The custom agent file (.agent.md) has a YAML header that names the agent and lists the tools that it may use. Its body sets the scope, the mandatory behaviour and the completion contract.

  • Skill files (SKILL.md) are reusable instruction sets. One skill holds the release-note workflow. Others hold the templates, the Flare formatting rules, the style guide, the audience rules and the product-name variables.

  • Prompt files (.prompt.md) hold short instructions for steps that repeat in every run, such as the preflight checks and the end-of-run memory update.

  • The workspace configuration file lists the repositories, the folders that the agent may write to and the rules that map a planned release to a folder.

  • The Model Context Protocol (MCP) server for Azure DevOps gives the agent controlled access to Azure DevOps. MCP is an open standard for connecting AI agents to external systems. Through the server, the agent queries work items, reads their relations, creates and links tasks, and updates their state, without direct access to the database.

  • Work Item Query Language (WIQL) queries return flat lists of work items. Batched reads with a limited field set keep a run over many items fast and within payload limits.

  • The memory file holds reusable lessons, such as a user correction or a special case. The agent reads the file at the start of a run and adds to it at the end.

  • MadCap Flare is the output format. The agent edits the XML-based .htm topic files and uses the project styles, spans and snippets.

  • Git records every change to the agent, the skills and the content as a reviewable commit.

Note: The tool list in the agent file limits what the agent can do. The agent cannot run code or browse the web.

Architecture

The design separates three concerns, so that each can change without breaking the others.

  • The agent file orchestrates the run. It is short by design. It sets the scope, restricts the tools and names the workflow skill as the single source of truth. It does not repeat the business rules.

  • The workflow skill holds the rules for item qualification, task creation, state gates, release destination, duplicate detection, the task description format and the summary format.

  • The content skills hold the writing rules. They apply in a fixed order: template and structure, Flare markup, product-name variables, audience, and then the style guide. Structure and markup have the final say. Wording rules work inside that structure.

This mirrors a common software pattern: a thin controller, a business-logic layer and reusable rule libraries.

Technical workflow

A run follows these steps in order.

  1. The agent accepts one or more work items, a parent item or a query. It never assumes that the first item is the target. If the item is a container such as a delivery item or user story, the agent expands the hierarchy to find the issue records that it contains.

  2. The agent checks each candidate against its product type and the qualification rules: a bug identification number, customer validation where required, the record type and exclusion of ported copies of a fix.

  3. The agent reads the live relations of each issue to find an existing documentation task. It reuses an existing task, and a completed task ends the work for that item.

  4. The agent writes entry text only when the fix is in the done state. Until then, the agent creates or confirms the task and reports the item as not ready.

  5. The agent resolves the release-note topic from the product type, the planned release and the repository structure. When the release is missing or cannot be mapped, the agent uses the work-in-progress folder and records the reason.

  6. Before drafting, the agent searches the destination for the bug identification number. If the number is already there, the agent adds no row.

  7. The agent reads the description and discussion of the source item, and writes the entry from confirmed facts only. The template, formatting rules, product variables, audience rules and style guide then shape the text in that order.

  8. The agent adds one row to the correct table, re-reads the file to confirm the change, and updates the Azure DevOps task with the description, assignee and state. A run summary closes the process.

Design principles

The project is built on rules, sequence and guardrails rather than on a single prompt. The stages always run in the same order: preflight, triage, task checks, state gate, destination, drafting and update. This keeps the behaviour consistent.

The customer-facing item is often a child or grandchild of the requested item. The agent therefore expands the hierarchy before it decides that an input is not relevant.

The agent does not create duplicate tasks, does not write outside the configured release-note folders and does not state anything that the source records do not support. Structure and markup are final. The style guide improves the wording inside that structure and cannot change the template or the markup.

Each run records the outcome, target file and task state for every item, so that a reviewer can audit what happened.

Controls for a reliable agent

An agent that edits files and updates a work-tracking system needs controls. The project uses the following.

  • The run moves through numbered stages, each with a defined output and a stop condition. The agent carries data forward only when the next stage needs it.

  • The agent can read, search, edit and use memory, and it can call the Azure DevOps tools. The configured release-note folders limit its file edits.

  • Early stages request classification fields only. The agent reads descriptions, discussions and attachments only for items that pass the gates, which reduces cost and noise.

  • The agent drafts facts as plain text first. The style pass then changes wording only, and markup is applied last without changing the wording. A pre-save checklist and a re-read of the saved file confirm that only the intended row or table changed.

  • Every statement must trace to the work item or its discussion. The agent leaves out any detail that is not confirmed.

  • The agent reads back created tasks and links. It retries failed or partial results once, for the missing items only.

  • The agent asks open questions in one message. Risky actions, such as moving content to a previous-releases topic, need confirmation.

  • Progress narration stays short, but the content and the run summary are never shortened.

  • Corrections from real runs go back into the skill and the memory notes. In one test run, the agent stopped at a parent item and never reached the customer problem under it. The fix was an explicit rule to expand child and grandchild records.

Outcome

In Copilot Chat, you select the agent and supply work item numbers, a parent item or a query. One run then does the following:

  1. Finds the customer-facing issues, including those nested under parent items, and skips the ones that do not qualify.

  2. Creates a documentation task for each qualifying issue that has none, copies the area, sprint, owner and planned release, and links the task to the issue.

  3. Adds a complete fix entry to the correct release-note topic in the Flare project, or to the work-in-progress folder when the release is not yet known. The entry uses the project template, styles and product variables.

  4. Skips issues that are already documented, and records why.

  5. Writes the task description with the issue reference, the status, the entry as saved in the topic and the file that was updated.

  6. Assigns the task to the current user and sets it to Review.

  7. Ends with a run summary that lists every task created or changed, every file updated and every item skipped, with the reason.

The technical writer or project stakeholder then reviews the text in the task and in the topic. This is the human-in-the-loop step: a person checks the facts and the wording, then edits or approves them. Triage, task handling, file lookup, duplicate checks and drafting are already complete.

For a batch of issues, a short review replaces hours of manual searching, copying and updating.

The project also shows the wider skill that this work needs: designing the system around the AI model, including the rules, the tool access, the data flow, the validation and the feedback loop.
